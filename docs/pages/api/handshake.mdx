# Handshake Protocol

This page documents the wire protocol used to establish an openlv session: the signaling frame format, every packet exchanged during the handshake, the order they are sent in, and how transport negotiation happens afterwards.

The handshake runs over the [signaling](/api/signaling) layer on untrusted public infrastructure.
Everything the relay sees is ciphertext; the relay only learns timing, message sizes, and the session topic.

## Roles

| Role | Also called | Typical deployment |
|------|-------------|--------------------|
| **Host** | Advertising peer | The dApp — creates the session URI and shows the QR code |
| **Client** | Joining peer | The wallet — scans the URI and joins the session |

The roles are only asymmetric during the handshake. Once the transport is connected, both sides are equal peers.

## Frame format

Every signaling frame published to the relay is a single string:

```text
<prefix><recipient><ciphertext>
```

| Position | Values | Meaning |
|----------|--------|---------|
| `prefix` | `h` | Encrypted with the **handshake key** `k` from the session URI, or the saved resumption secret (AES-GCM) |
| | `x` | Encrypted with a directional **peer-bound session key** (AES-256-GCM) |
| `recipient` | `h` | Intended for the host |
| | `c` | Intended for the client |
| `ciphertext` | base64 | The encrypted JSON packet |

So a frame starting with `hc` is a handshake-key encrypted message addressed to the client, and `xh` is a session-key encrypted message addressed to the host. The prefix and recipient are authenticated as associated data.
Receivers silently drop frames not addressed to their role, frames that fail to decrypt, and decrypted payloads that don't match a known packet shape.

## Packets

Every decrypted payload is a JSON object with three fields:

```typescript
type SignalMessage = {
  type: "flash" | "pubkey" | "capabilities" | "data";
  payload: unknown;
  timestamp: number; // Unix ms at send time
};
```

### `flash`

Sent by the **client** to kick off the handshake, encrypted with the handshake key `k`.
The payload contains a fresh 16-byte nonce as 32 lowercase hex characters.

```json
{ "type": "flash", "payload": { "nonce": "<32 lowercase hex characters>" }, "timestamp": 1750000000000 }
```

### `pubkey`

Carries a peer's encryption public key. Sent twice per handshake:

1. **Host → client** under the handshake key, in response to `flash`.
2. **Client → host** under the handshake key, after verifying the host key.

```json
{
  "type": "pubkey",
  "payload": { "publicKey": "<serialized X25519 public key>", "clientNonce": "<client nonce>", "hostNonce": "<host nonce>" },
  "timestamp": 1750000000000
}
```

The client verifies the host's key against the `h` parameter from the session URI (the first 16 lowercase hex characters of SHA-256 of the 32 raw X25519 public-key bytes).
A mismatch causes the packet to be ignored.

### `capabilities`

Completes the handshake: it acknowledges the previous step, negotiates the transport, and shares peer metadata in a single packet. Sent twice:

1. **Host → client** once the host has recorded the client's key — this doubles as the delivery receipt for the client's `pubkey`.
2. **Client → host** to finish — this doubles as the delivery receipt for the host's `capabilities`.

Capabilities are encrypted with keys derived from the X25519 shared secret, bootstrap secret, session ID, roles, public keys and both nonces. Each peer confirms possession of the derived key before accepting the other. Peer metadata remains self-reported, not verified real-world identity.

```typescript
type SignalMessageCapabilities = {
  type: "capabilities";
  payload: {
    /** Supported transports, in preference order. */
    transports: ("wrtc" | "ws" | string)[];
    /** Optional self-description shown in the other peer's UI. */
    info?: {
      /** Reverse-DNS application identifier. */
      identity: string;   // "com.example.wallet"
      name: string;       // "Example Wallet"
      icon?: string;      // data URI or image URL — see below
    };
  };
  timestamp: number;
};
```

```json
{
  "type": "capabilities",
  "payload": {
    "transports": ["wrtc", "ws"],
    "info": {
      "identity": "com.example.wallet",
      "name": "Example Wallet",
      "icon": "data:image/png;base64,…"
    }
  },
  "timestamp": 1750000000000
}
```

Transport identifiers: `wrtc` ([WebRTC](/api/transport/webrtc)) and `ws` (relayed WebSocket, planned as a fallback for ICE-hostile networks).
Unknown identifiers are skipped, not fatal — a peer can advertise transports the other side has never heard of.

The `icon` may be a data URI or an image URL.
The wire only enforces its size (8 KB max — a receiver drops the whole packet beyond that, and a sender must refuse to send it); whoever renders or fetches the icon is responsible for sanity-checking it first, since it comes from the remote peer.
Some signaling protocols enforce small message limits (ntfy in particular), and the whole packet must survive base64 + encryption overhead — inline icons should be tiny (think 64×64 PNG), with a URL as the alternative for richer artwork.

#### Transport selection

Both `transports` lists are preference-ordered. The selected transport is the **first entry in the host's list that also appears in the client's list**.
Both sides compute this independently once they hold both packets — no extra confirmation round trip is needed.
An empty intersection fails the session with a "no common transport" error (signaling itself stays `ENCRYPTED`; the session disconnects).

### `data`

The only packet allowed after the handshake completes. Always session-key encrypted.
Its payload is opaque to the signaling layer — it carries the [transport negotiation](#transport-negotiation) envelope for the selected transport.

```json
{ "type": "data", "payload": { "...": "..." }, "timestamp": 1750000000000 }
```

## Handshake sequence

The complete flow from URI creation to a connected peer-to-peer transport:

```mermaid
sequenceDiagram
    autonumber
    participant D as dApp (host)
    participant W as Wallet (client)

    Note over D: Generates sessionId, keypair,<br/>handshake key k, pubkey hash h
    D--)W: openlv:// URI via QR code or link (out-of-band)
    Note over D,W: Both subscribe to the sessionId topic.<br/>Every arrow below is a relayed frame — the relay only sees ciphertext.

    W->>D: flash (client nonce) · handshake-key frame (hh)
    D->>W: pubkey (host key and nonces) · handshake-key frame (hc)
    Note over W: Verify SHA-256(host key)<br/>matches h from the URI
    W->>D: pubkey (client key and nonces) · handshake-key frame (hh)
    Note over D,W: Derive directional session keys
    D->>W: capabilities · session-key frame (xc)
    W->>D: capabilities · session-key frame (xh)
    Note over D,W: Signaling ENCRYPTED — transport selected

    D->>W: data { type: "offer" }
    W->>D: data { type: "answer" }
    D->>W: data { type: "candidate" } · repeated
    W->>D: data { type: "candidate" } · repeated
    Note over D,W: WebRTC data channel opens — transport CONNECTED
    D-)W: session envelope (request / response / failed / ack) · direct P2P
```

In packet order:

| # | Direction | Packet | Encryption | Purpose |
|---|-----------|--------|------------|---------|
| 1 | client → host | `flash` | handshake key | Announce presence and client nonce |
| 2 | host → client | `pubkey` | handshake key | Share host public key and host nonce |
| 3 | client → host | `pubkey` | handshake key | Share client public key after verifying `h` |
| 4 | host → client | `capabilities` | host-to-client session key | Confirm key possession; offer transports + info |
| 5 | client → host | `capabilities` | client-to-host session key | Confirm key possession; answer transports + info |
| 6+ | both | `data` | directional session key | Transport negotiation |

## Delivery, retries, and state

Signaling relays are lossy (MQTT QoS 0, ntfy is best-effort), so handshake frames are re-sent every 2 seconds. Receivers answer duplicates with the cached response.
If the client keeps receiving the host's `capabilities` after finishing, its own final packet may have been lost, and it sends the same cached response again.

```mermaid
stateDiagram-v2
    [*] --> STANDBY
    STANDBY --> CONNECTING: setup()
    CONNECTING --> READY: subscribed to topic
    READY --> HANDSHAKE: resuming with saved credentials
    READY --> HANDSHAKE: flash sent (client) /<br/>flash received (host)
    HANDSHAKE --> HANDSHAKE_PARTIAL: peer pubkey recorded
    HANDSHAKE_PARTIAL --> ENCRYPTED: capabilities received
    HANDSHAKE --> ERROR: signaling failure
    HANDSHAKE_PARTIAL --> ERROR: signaling failure
```

After pairing, peers save their static keys, pinned peer key, signaling parameters and a separate resumption secret. Resumption repeats the handshake with fresh nonces and the saved secret; the invitation alone cannot resume a pairing. A restarting host sends a bootstrap-encrypted `flash` with `wake: true`; the client echoes its nonce in `wakeNonce`, and the host ignores responses to old wakes. Treat saved credentials as secrets.

Each directional signaling and transport channel has a 256-message replay window. Static X25519 key agreement does **not** provide forward secrecy. The pre-release version 1 wire format and saved credentials changed; earlier peers must pair again. See the protocol specification for the key schedule and serialization.

## Transport negotiation

Once signaling is `ENCRYPTED`, the selected [transport](/api/transport) negotiates a direct connection by exchanging `data` packets. For WebRTC the payloads are:

```json
{ "type": "offer",     "payload": "<JSON-encoded SDP offer>" }
{ "type": "answer",    "payload": "<JSON-encoded SDP answer>" }
{ "type": "candidate", "payload": "<JSON-encoded ICE candidate>" }
```

The host creates the [WebRTC](/api/transport/webrtc) data channel and sends the `offer`; the client answers; both sides trickle ICE `candidate` messages until the channel opens.
From that point all application traffic flows over the direct transport using the session envelope:

```json
{ "type": "request",  "messageId": "<uuid>", "payload": { "jsonrpc": "2.0", "id": 1, "method": "eth_requestAccounts", "params": [] } }
{ "type": "ack",      "messageId": "<uuid>" }
{ "type": "response", "messageId": "<uuid>", "payload": { "jsonrpc": "2.0", "id": 1, "result": ["0x1234…"] } }
{ "type": "failed",   "messageId": "<uuid>" }
```

The receiver acks a request immediately (so the sender knows the peer is alive while the user decides), then sends the correlated `response` when the handler resolves.
If the handler throws, the receiver sends `failed` instead. It carries no detail.
This session-envelope `ack` is a per-request receipt inside the established session — unrelated to the signaling handshake.
